# PPE 智能监控系统 — 风险分析与管控措施

> 飞腾派 E2000Q 异构多核平台 | 双生序章团队

## 1. 系统概述

本系统基于飞腾 E2000Q 四核异构平台 (2大核 + 2小核) 构建，采用 Linux + Bare-Metal 异构多核架构，通过 OpenAMP RPMsg 实现主从核实时通信。系统具备 AI 视觉检测、物理传感器监控、硬件声光告警等关键安全功能。

本文档针对系统在实际工业应用场景中可能面临的风险进行详细分析，制定基于飞腾芯片特性的管控措施，并设计 FIT (Fault Injection Test) 故障注入测试方案验证管控措施的有效性。

## 3. 详细风险分析

### R1: 通信不可靠 (RPMsg 通道故障)

**风险描述**: 主核 (Core 0 Linux) 与从核 (Core 1 Bare-Metal) 之间的 OpenAMP RPMsg 通道可能因硬件异常、驱动故障或软件崩溃而断开。

**影响分析**:
- 主核无法向从核下发蜂鸣器控制指令
- 从核的传感器报警数据无法上报到 UI
- 系统丧失物理层感知能力

**管控措施** (代码位置: `rpmsg_node.cpp:rx_task()`):
- 主核每 5 秒向从核发送 `DEVICE_CORE_CHECK` (0x0003) 心跳包
- 从核在 `rpmsg_endpoint_cb()` 中原样回复（已有逻辑）
- 主核 15 秒内未收到回复 → 设置 `heartbeat_ok = false`
- UI 定时器读取该状态，将 RPMsg 徽章变为红色 "● RPMsg 断连"
- 心跳恢复后自动切换回绿色 "● RPMsg 正常"

**FIT 测试方案** (脚本: `tests/fit_rpmsg_disconnect.sh`):
1. 正常启动系统，确认 RPMsg 连接
2. 执行 `echo stop > /sys/class/remoteproc/remoteproc0/state`
3. 等待 15 秒
4. 验证主核日志出现 "🚨 [心跳超时] 从核通信中断！"
5. 恢复从核，验证 "💚 [心跳] 从核通信恢复！"

---

### R2: 主控程序跑飞 (Linux 进程崩溃)

**风险描述**: 主核系统可能因段错误、内存耗尽或 OOM Killer 被强制终止，此时从核的蜂鸣器处于不确定状态。

**影响分析**:
- 如果崩溃前蜂鸣器处于开启状态，会持续鸣响造成恐慌
- 如果崩溃前蜂鸣器处于关闭状态，可能遗漏真实报警
- 从核失去主核的控制指令来源

**管控措施** (代码位置: `slaver_00_example.c:FRpmsgEchoApp()`):
- 从核独立运行看门狗计数器 `wdt_counter`
- 收到心跳包时清零计数器（喂狗）
- 超过 `WDT_TIMEOUT_TICKS` (~10秒) 无心跳 → 进入安全状态:
  - `Buzzer_Set(0)` — 主动关闭蜂鸣器
  - `flag_ai_alarm_req = false` — 清除 AI 告警标志
- **设计理念: 失效即安全 (Fail-Safe)**

**FIT 测试方案** (脚本: `tests/fit_main_crash.sh`):
1. 启动系统，触发 AI 违规告警使蜂鸣器开启
2. `kill -9 $(pidof ppe_system)`
3. 等待 12 秒
4. 验证蜂鸣器自动关闭
5. 验证从核串口出现 "主核心跳超时！从核进入安全状态 (Fail-Safe)"

---

### R3: 安全数据损坏 (通信完整性)

**风险描述**: RPMsg 基于共享内存实现，数据可能因电磁干扰、DMA 竞争或内存翻转导致损坏。

**影响分析**:
- 损坏的命令字可能触发非预期的硬件操作
- 损坏的传感器数据可能导致误报或漏报

**管控措施** (代码位置: 主从双侧协议栈):
- `data_packet` / `ProtocolData` 末尾新增 `uint8_t crc8` 字段
- 发送方: 使用 CRC-8/MAXIM 算法 (多项式 0x31) 计算校验码
- 接收方: 校验 CRC8，不匹配则丢弃并递增错误计数
- UI 面板实时展示 CRC 错误累计次数

**FIT 测试方案** (脚本: `tests/fit_crc_corrupt.sh`):
1. 向 `/dev/rpmsg0` 写入 5 包随机数据
2. 验证主核日志出现 "⚠️ [CRC] 数据校验失败"
3. 验证 UI CRC 计数增长
4. 验证系统功能不受影响

---

### R4: 关键数据资源损坏 (磁盘溢出)

**风险描述**: 违规截图持续写入可能耗尽 SD 卡/eMMC 存储空间。

**管控措施** (代码位置: `io_node.cpp:check_and_cleanup_disk()`):
- 每 500 次写入检查磁盘使用率
- 使用率 > 85% 时自动删除最旧的 20% 图片
- 日志文件保持增量追加

**FIT 测试方案** (TC-08 已有):
- 使用 `dd` 填满磁盘 → 触发清理 → 验证恢复

---

### R5: 安全功能失效 (模型缺失)

**风险描述**: NCNN INT8 模型文件被意外删除或损坏。

**管控措施** (代码位置: `inference_node.cpp`):
- 模型加载失败时打印错误日志
- 安全退出进程，不执行后续推理

**FIT 测试方案** (脚本: `tests/fit_model_missing.sh`):
- 删除模型文件 → 启动系统 → 验证优雅退出 → 恢复文件

---

### R6: 传感器信号干扰 (电磁误报)

**风险描述**: 火焰传感器在电磁复杂环境下可能产生毛刺信号。

**管控措施** (代码位置: `rpmsg_node.cpp:rx_task()`):
- **非对称滞回去抖状态机**:
  - 触发要"慢": 连续 3 次火警确认 (2 秒窗口内)
  - 解除要"更慢": 必须沉默 3 秒才解除
- 防止信号间隙导致红绿闪烁

---

### R7: 外设硬件损坏/断线 (Hardware Failure)

**风险描述**: 火焰/有害气体传感器或蜂鸣器由于现场工业环境问题导致接线松脱、引脚开路，或者元器件本身损坏失效。

**管控措施**:
- **从核启动与运行自检**：从核（Core 1 Bare-Metal）在启动阶段检测物理引脚输入电平，对 I2C 传感器进行 ACK 握手扫描，超时或无应答则向上级主核发送错误代码，由主核 UI 报警提示。
- **报警回路环路诊断**：从核在输出高电平拉高控制蜂鸣器时，同步通过另一个反馈引脚进行状态回读（Loopback），若控制电平与物理引脚状态不匹配，判定为报警回路损坏或断线。

**验证方法 (万用表物理测试)**:
1. 在系统运行中，物理断开蜂鸣器或气感传感器连接线。
2. 触发 AI 违规报警，使用万用表直流电压档测量开发板对应的输出引脚（如 GPIO1_15），读取电平是否从 0V 变为 3.3V，验证控制信号输出正常。
3. 使用万用表电阻/导通档测量外设端子，确认其物理开路（阻值无穷大）。
4. 验证从核终端输出引脚故障日志，且 Qt 监控主屏弹出“外设故障报警”提示。

---

### R8: 网络不可达 (API 降级)

**管控措施** (代码位置: `deepseek_worker.cpp`):
- HTTP 请求设置 10 秒超时
- 超时或错误 → 自动回退到 `getFallbackAdvice()` 预设建议
- 日志标记 "使用降级预设建议"

## 4. 飞腾芯片特性与安全设计的关联

| 飞腾芯片特性 | 安全设计应用 |
|------------|------------|
| **异构多核 (FTC310 × 4)** | 从核裸机独立运行看门狗，不受 Linux 内核故障影响 |
| **OpenAMP 框架** | 心跳检测基于已有的 RPMsg 通道，零额外硬件成本 |
| **GPIO 中断 (FGpio)** | 火焰传感器边缘触发，ISR 内直接执行仲裁，微秒级响应 |
| **共享内存 (remoteproc)** | CRC8 校验保护共享内存数据完整性 |
| **PSCI 接口** | `FPsciCpuOff()` 实现从核安全关闭 |
