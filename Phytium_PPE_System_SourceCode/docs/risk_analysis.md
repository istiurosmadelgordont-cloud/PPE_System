## 2. 异构多核关键功能风险管理闭环设计 (7.2)

### 2.1 应对【主控程序死锁】：主从心跳与看门狗重启 (7.2.1)
*   **失效机理**：主核 Linux 上的 `ppe_system` 进程发生非优雅的僵死或卡死（例如主线程死锁），此时主进程无法向从核下发报警控制字，从核若继续维持旧状态将造成漏报。
*   **管控策略**：主核 heartbeat 线程以 500ms 周期向从核发送心跳数据。从核通过 generic timer 计时，一旦连续 4 次心跳包丢失（共 2s），判定主核发生了非优雅死锁，立即鸣笛报警并停止向 `FWDT0` 看门狗喂狗，10s 超时后触发 SoC 硬件冷重启。
*   **验证方法**：发送 `kill -STOP` 挂起主进程，验证从核在 2s 内响起警报，并在后续看门狗超时后系统冷重启。

### 2.2 应对【应用进程不响应】：AMP 物理隔离与硬中断接管 (7.2.2)
*   **失效机理**：主核 Linux 内核崩溃（Kernel Panic）或遭遇 OOM 死锁，主控系统整体失去响应。
*   **管控策略**：基于飞腾派的异构多核物理隔离，Core 1 从核裸机不受主核 Linux 内核的任何状态影响。火焰传感器引脚绑定到从核物理 EXTI 中断上，直接在从核 Baremetal 执行仲裁。
*   **验证方法**：使用 `stress-ng` 挂起 Linux 所有大核，手动触发火焰传感器，验证蜂鸣器依然能在微秒级内拉高响应。

### 2.3 应对【输入端传感器损坏】：传感器极值校验与离线隔离 (7.2.3)
*   **失效机理**：温湿度探头（AHT20/DHT11）在运行过程中脱落损坏，或者 MQ-2 有害气体传感器硬件烧毁，导致输入信号丢失或返回高阻态/全零乱码。
*   **管控策略**：从核驱动层为 I2C 传输设置 100ms 超时限制，防止传感器死锁阻塞从核的 OpenAMP 主循环；在从核读取逻辑中加入突变量极值过滤（如单次跳变超 15°C 视为噪声丢弃），当判定传感器损坏时，向上级主核发送离线故障字，在 Qt GUI 大屏幕上将温湿度框显式置黄，提示“环境探头异常”。
*   **验证方法**：物理拔掉 I2C 数据线，观察从核输出跳过日志，主核 UI 对应数值显示为黄色故障标识。

### 2.4 应对【控制数据传输异常】：异构通信链路串扰与 RPMsg 帧校验 (7.2.4)
*   **失效机理**：共享内存段在工业现场强电磁干扰下产生随机 Bit 翻转，或发生了非预期的内存踩踏，导致通信指令被篡改。
*   **管控策略**：主从双侧的 RPMsg 协议栈数据帧尾均附加 **CRC-8/MAXIM** 校验值。接收端重新计算校验和，一旦发现与包尾 `crc8` 不匹配，立即将该控制帧丢弃并不予执行，防止硬件误动作，同时在 UI 看板累加通信错误计数。
*   **验证方法**：向控制字符设备 `/dev/rpmsg0` 写入随机干扰数据，验证从核无异常动作。

### 2.5 应对【断电数据保存失败】：告警证据原子写入防损毁 (7.2.5)
*   **失效机理**：违规截图在写入磁盘文件期间，现场设备突然断电，导致磁盘上留有一张 0 字节或半截损坏的不可读 JPEG。
*   **管控策略**：`io_node` 在写盘时先保存为临时文件 `xxx.jpg.tmp`，在文件完全编码落盘并调用 `fsync` 后，再执行 Linux 文件系统的原子重命名操作：`rename("xxx.jpg.tmp", "xxx.jpg")`。
*   **验证方法**：在触发违规存图的瞬间直接拔掉开发板电源，重新开机后验证抓拍目录中不存在任何损坏的残缺图。

### 2.6 应对【关键功能部件损坏】：AI 权重损坏与启动检测 (7.2.6)
*   **失效机理**：YOLO 权重文件（`model1_int8.bin`）在 SD 卡中发生物理损坏或被意外删改。
*   **管控策略**：AI 推理线程在启动时执行模型合法性与校验和检测，一旦加载失败，优雅退出当前 AI 推理主环，并向从核发送 `DEVICE_CORE_SHUTDOWN`，防止以错误状态指导物理外设。
*   **验证方法**：人为删除或清空模型权重文件，启动系统，验证其优雅报错退出且界面指示灯变红。

### 2.7 应对【安全数据非法访问】：权限隔离与属主控制 (7.2.7)
*   **失效机理**：非授权用户通过 SSH 或本地终端越权删除、修改违规抓拍存图，导致取证证据丢失。
*   **管控策略**：违规抓拍输出目录 `violations_data/` 使用 `chmod 700` 进行严格的读写执行限制，并设定其属主为 `root`。普通用户无读写权。
*   **验证方法**：切换普通用户 `user` 访问抓拍目录，验证报错 `Permission denied`。

### 2.8 应对【AI 推理线程静默失效】：看门人时间戳监控 (7.2.8)
*   **失效机理**：AI 视觉推理线程发生异常卡死（静默失效），但主进程和心跳线程仍然存活且在持续向从核应答心跳，导致从核误判主核一切正常，造成安全漏报。
*   **管控策略**：主进程的 heartbeat 心跳线程引入“看门人监控（Watchdog Daemon）”机制，每周期检测 AI 线程写入的最新帧处理时间戳。若判定 AI 线程已超过 3 秒未更新时间戳，心跳线程主动停止向从核发送心跳，以此诱导从核触发 R1 闭环进行声光接管并冷重启。
*   **验证方法**：在后台线程中强行挂起 AI 推理循环，验证主进程心跳在 3s 后中断，从核成功接管长鸣。

### 2.9 应对【潜在系统风险】：存储满载监控与防洪自清洁 (7.2.9)
*   **失效机理**：高频抓拍存图使 SD 卡存储完全写满，导致 Linux 系统分区锁死，业务中断。
*   **管控策略**：`io_node` 写盘前调用 `statvfs` 读取剩余扇区。当分区整体占用率突破 **85%** 阈值时，自动触发自清洁：按时间戳从小到大升序排序，清除最旧的 1500 张历史抓拍图片。
*   **验证方法**：向磁盘写入大文件使分区超 85%，触发一次违规，验证成功自动清除旧图腾出空间。

### 2.10 应对【输出端报警器物理损坏】：硬件回路探伤自检机制 (7.2.10)
*   **失效机理**：声光报警器或驱动三极管物理损坏、开路或短路，导致即使主从核下发控制信号，现场也无法发出警报，失去事故干预能力。
*   **管控策略**：从核 Baremetal 在拉高报警 GPIO1_15 控制脚时，同步开启一条反馈检测引脚采样。如果采样电平与控制电平不匹配，判定为报警物理回路开路故障，从核立即通过 RPMsg 将错误码上传至主核，GUI 界面徽章变为黄色警告并弹出“声光报警器故障”，同时导出人工排查 SOP 手册。
*   **验证方法**：物理断开蜂鸣器控制线，触发一次 AI 违规，观察 Qt 看板状态栏瞬间弹出“声光报警器故障”预警。
