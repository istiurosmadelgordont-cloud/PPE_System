# 📖 PPE 智能监控系统 — 安全可靠性设计说明

> **设计宿主**：飞腾派 E2000Q 异构多核平台 | 双生序章团队  
> **文档说明**：本报告详述了系统基于飞腾 E2000Q 异构多核架构的底层高可靠性安全闭环设计，对齐风险管理 10 大失效场景（FMEA 7.2.1 ~ 7.2.10）的缓释防御手段。

---

## 1. 核心安全设计理念

本系统的安全可靠性设计遵循以下三大原则：

### 1.1 异构隔离 (Heterogeneous Isolation)

利用设备树（DTS）对飞腾派 E2000Q 的四核进行物理级切分，划分出物理隔离的两个执行域：

```
    ┌──────────────────────────────────┐    ┌──────────────────────────┐
    │        Linux 域 (Core 0/2/3)      │    │  Bare-Metal 域 (Core 1)   │
    │                                    │    │                          │
    │  ┌─────────┐  ┌────────────────┐  │    │  ┌──────────────────┐   │
    │  │ Qt GUI   │  │ NCNN AI 推理    │  │    │  │ GPIO 中断处理     │   │
    │  │ Core 0   │  │ Core 2+3       │  │    │  │ 蜂鸣器控制        │   │
    │  └─────────┘  └────────────────┘  │    │  │ 看门狗             │   │
    │        │              │            │    │  └──────────────────┘   │
    │        │    RPMsg (共享内存)       │◄──►│      OpenAMP             │
    │        ▼                          │    │                          │
    │  ┌──────────────────────────┐    │    │  ✅ 独立于 Linux 内核     │
    │  │ IO 存储 / DeepSeek API   │    │    │  ✅ 零 OS 调度开销        │
    │  │ 异步落盘 / 水位清理机制   │    │    │  ✅ 微秒级硬件中断响应    │
    │  └──────────────────────────┘    │    │  ✅ 独立外设驱动控制      │
    └──────────────────────────────────┘    └──────────────────────────┘
```

*   **安全意义**：从核运行于 Baremetal 裸机环境，完全独立于 Linux 内核。即便主核发生 Kernel Panic、内核死锁或 OOM 强杀，从核的传感器监控和蜂鸣器物理控制仍能正常运行，实现物理级的故障隔离。

### 1.2 失效即安全 (Fail-Safe)

当系统面临 10 大潜在失效场景时，均设计了对应的优雅降级或硬件复位安全防御动作：

| 对应风险编号 | 潜在失效场景 (FMEA) | 默认安全动作 (Fail-Safe) | 实现逻辑与物理机制 |
| :---: | :--- | :--- | :--- |
| **R1** | **主控程序跑飞/死锁** | 从核自主接管报警并重启芯片 | 500ms 心跳超时（2s）触发蜂鸣器长鸣，从核停止喂狗，WDT0 触发片上 Cold Reset |
| **R2** | **主核应用不响应/死机** | 从核独立报警与物理阻断 | 裸机 EXTI 中断优先级 0，微秒级抢占响应，绕过 Linux 内核调度 |
| **R3** | **传感器硬件损坏/脱落** | 启动检测跳过，数值离线预警 | 引入 I2C 读取超时退出机制防死锁，UI 温度数值显式置黄告警 |
| **R4** | **非法控制数据/通信串扰** | 非法数据包过滤拦截 | 数据包附加 **CRC-8/MAXIM** 校验码，计算不匹配则丢弃数据帧 |
| **R5** | **断电保存失败/图片损坏** | 磁盘文件原子保护 | **原子重命名机制**：图片写盘先写 `.tmp` 文件，完成后调用系统 `rename` |
| **R6** | **关键权重模型缺失** | 优雅退出，防异常控制状态 | 启动时执行 bin/param 完整性校验，失败则向从核下发 Shutdown 并关闭主核 AI |
| **R7** | **安全数据非法访问** | 文件读写权限隔离拦截 | 抓拍目录设为 root 独占，并执行 `chmod 700` 文件属主隔离限制 |
| **R8** | **主程序意外终止/强退** | 物理声光告警归零复位 | 注册 `SIGINT` 和 `SIGTERM` 信号捕获，退出时自动下发蜂鸣器低电平指令 |
| **R9** | **存储满载系统死机** | 后台自清洁，自动腾退空间 | `io_node` 监控分区水位，超 85% 触发自动清理 1500 张最旧历史抓拍 |
| **R10**| **外设不可逆物理损坏** | 硬件探伤预警，导出排查 SOP | 物理回路阻抗变化探伤，UI 黄灯闪烁指示，导出排查 SOP 指导手册 |

## 2. 双向监督架构机制

主从核之间通过一套周期性心跳机制维持物理互锁：

```
       主核 (Linux Core 0)               从核 (Baremetal Core 1)
       ┌───────────────┐                  ┌───────────────────┐
       │ 心跳包发送     │  ─── 心跳包 ───►  │ ept 回调接收       │
       │ (周期 500ms)  │  ◄── 应答包 ───  │ 重置 miss 计数为0 │
       │               │                  │                   │
       │ 15秒接收超时  │                  │ 2秒(4次miss)超时  │
       │ 触发 UI 告警  │                  │ 触发 Fail-Safe    │
       └───────────────┘                  └───────────────────┘
```

*   **主核监督从核**：主核通过定时器监测应答。若连续 15s 未收到从核回复，将大屏看板上的“RPMsg 通信”状态徽章变红报错。
*   **从核监督主核**：从核主循环利用 generic timer 进行 500ms 滴答计数。一旦计数累加达到 4 次（2s 周期）仍未收到主核心跳，从核进入安全接管模式（长鸣报警，缩短 WDT0 溢出时间为 1s 并停止喂狗，直至 SoC 冷重启自愈）。

## 3. 跨核通信数据完整性校验 (CRC8)

在共享内存通信总线上，所有通过 RPMsg 交互的数据包均进行 **CRC-8/MAXIM** 校验：

*   **数学多项式**：\(x^8 + x^5 + x^4 + 1\) (0x31)。
*   **校验过程**：发送端对 `command` + `length` + `data` 计算 CRC 校验码并写入包尾的 `crc8` 字段；接收端获取数据后进行二次校验。
*   **安全价值**：即使物理总线因车间电磁辐射发生位翻转（Bit Flip）或共享内存踩踏，非法控制字也会在接收端瞬间被丢弃，确保动作逻辑绝对安全。
